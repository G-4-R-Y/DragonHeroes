# Research track: engine-netcode

## Summary
Godot 4.x in mid-2026: current stable is Godot 4.6 (released late Jan 2026), which brought RPC/bandwidth efficiency improvements, native Jolt physics (3D), and LibGodot embedding. The high-level multiplayer API (ENetMultiplayerPeer + RPCs + MultiplayerSpawner/MultiplayerSynchronizer) is good for prototyping but has documented ceilings for a game like Dragon Heroes: Rivet's testing found connection instability above ~40 CCU per server, and CipSoft (Tibia's developer) published a March 2026 post-mortem of an MMO tech demo on Godot 4.4.1/.NET where the high-level API over ENet "collapsed around 80–100 concurrent connections" (CPU spikes, mass disconnects on a 2-core VM); they fixed it by replacing the high-level API with a custom transport layer. The consensus 2026 pattern for a server-authoritative ARPG is: single Godot project exported two ways (client + headless Linux server via the official "dedicated_server" export feature that strips visual assets), custom byte-packed snapshot protocol over raw ENet/UDP (ENetConnection/ENetPacketPeer, skipping MultiplayerSynchronizer) or LiteNetLib if the server core is C#, with snapshot interpolation + client-side prediction + server-side lag compensation and grid/AOI interest management. Rollback netcode (godot-rollback-netcode has a Godot 4 port, last updated Aug 2025; netfox also implements rollback) is only viable for low-entity-count matches — it re-simulates N frames of the whole world per mispredict, so it cannot handle hundreds of creatures+projectiles; at most use it for an isolated 1v1 duel mode. netfox (v1.35.3, July 2026) is the most actively maintained Godot 4 netcode addon (CSP, reconciliation, lag compensation, interpolation, noray NAT punching) and is the best starting point or reference implementation.

Determinism and language: Godot's built-in physics (and Jolt-in-Godot) is floating-point and explicitly NOT deterministic across platforms — do not build lockstep/rollback on it. For a server-authoritative snapshot model you don't need determinism at all (recommended). If you do need it (replays, rollback duels), options are the Godot Rapier 2D/3D GDExtension (deterministic; a cross-platform-deterministic build exists with a performance penalty, no SIMD/parallel solving) or a fixed-point engine-agnostic sim core (e.g., the Klotho FP64 C# framework targets exactly this for Godot/Unity). On language: GDScript is the slowest and fine only for glue/content scripting; C# is substantially faster but pays marshalling costs at the engine boundary, is excluded from Godot's built-in profiler (CipSoft flagged this — you need Rider/dotTrace), and cannot call GDExtensions (no generated bindings). GDExtension C++/Rust is fastest (community benchmark: 10k physics checks/frame ~3.8ms in C# vs ~0.9ms in C++ GDExtension). For hundreds of creatures + projectiles per zone, the critical decision is architectural, not language: Godot's scene nodes are documented as suitable for "hundreds at most" — the sim must be data-oriented (plain arrays/structs in C# or a Rust/C++ GDExtension, using PhysicsServer2D/RenderingServer or your own hitbox math directly, MultiMesh for client rendering). Done that way, hundreds-to-low-thousands of active entities at 20–30 Hz server tick is achievable per zone process; done with Node-per-entity + MultiplayerSynchronizer it is not.

Hosting/orchestration had a shake-up: Hathora is gone — acquired by Fireworks AI (announced March 4, 2026), platform frozen and permanently shut down May 5, 2026, stranding shipped games like Stormgate (multiplayer went offline). Rivet has also pivoted its marketing toward AI-agent infrastructure. Surviving options with São Paulo coverage: (1) Agones (v1.59, July 2026, supports K8s 1.32–1.34) self-managed on GKE southamerica-east1, EKS sa-east-1, or AKS Brazil South — maximum control and no platform risk, but real DevOps cost; (2) Edgegap — managed container orchestration, 615+ edge locations across major clouds (which include São Paulo regions), free dev tier, pay-per-use ($0.00115/min per vCPU + $0.10/GB egress), Godot supported via generic Docker flow with an official Godot plugin in development; (3) W4 Cloud from W4 Games (founded by Godot maintainers) — AGPL open-source, self-hostable backend with matchmaking, auth, lobbies, and on-demand authoritative Godot server orchestration, plus a hosted SaaS. Gameye is another managed alternative. The Hathora lesson: keep game servers as plain Docker containers and orchestration behind a thin abstraction so you can migrate.

Engine comparison: Unity (6.x; Pro/Enterprise +5% price Jan 2026, several services moved to paid modular add-ons) has the most mature off-the-shelf netcode — Fish-Net is widely considered the most complete free option (mature client-side prediction, lag compensation, benchmarks >100 CCU comfortably), stronger than first-party NGO for a fast ARPG; Unity's 2D pixel-art tooling is fine but its content pipeline (Addressables, AssetBundles) and licensing add friction vs. Godot's open PCK patching. Bevy (0.18, March 2026) + lightyear or bevy_replicon offers the best raw server performance, ECS scaling to thousands of entities, prediction/rollback/interpolation and WebTransport built into lightyear, plus an existing Edgegap autoscaling template (bevygap) — but no real editor: weekly content drops become code/asset-pipeline work (LDTK/Tiled help for tiles only), and it needs a Rust-fluent team. MonoGame is fully DIY (LiteNetLib/Lidgren for transport; the official 2D networking bounty is stalled as of the Feb/May 2026 board minutes) — excellent pixel-art rendering control, worst content-iteration velocity. For a small Brazilian studio shipping weekly drops, Godot's editor iteration speed, zero licensing cost, and PCK-based content patching (ship new items/creatures/skills/biomes as data + PCK patches without full client rebuilds, with known caveats about patch dedup/size and no downloaded-code execution on iOS) is the strongest overall fit, provided the simulation/netcode core is custom (C# or Rust GDExtension) rather than the stock high-level API.

## Recommendations
- Use Godot 4.6+ with a single project exported two ways: client, and a headless Linux dedicated server using the official 'dedicated_server' export feature (strips textures/audio); containerize the server from day one (docker + `godot --headless` CI export).
- Do NOT build combat sync on MultiplayerSynchronizer/MultiplayerSpawner. Write custom netcode: raw ENet (ENetConnection/ENetPacketPeer) or LiteNetLib (if C# core) with byte-packed, delta-compressed snapshots at 20-30 Hz, client-side prediction + server reconciliation for the local hero, snapshot interpolation for everything else, and server-side lag compensation (rewind hitboxes) for hit registration. Use netfox (v1.35.x) as the base or reference implementation.
- Choose snapshot interpolation + prediction, not rollback, for the core game: rollback cannot scale to hundreds of creatures/projectiles. If 1v1 duels ever need frame-perfect feel, isolate them as a separate low-entity mode (godot-rollback-netcode Godot 4 port or netfox rollback).
- Skip physics determinism entirely (server-authoritative floats are fine). Keep combat math (hitboxes, projectiles) as your own simple 2D geometry code on a fixed timestep rather than relying on the physics engine; if you ever need determinism, use Godot Rapier 2D or a fixed-point core, not Godot/Jolt physics.
- Build the zone simulation data-oriented and engine-agnostic: entities as plain arrays/structs, not Nodes (Godot nodes are for 'hundreds at most'). Language: C# for the server sim is the pragmatic choice for a small team (mind the missing built-in profiler; budget for Rider/dotTrace); Rust/C++ GDExtension if you need max headroom (roughly 4x C# in tight loops) — but note C# cannot call GDExtensions, so pick one path for the sim core. GDScript only for UI/content glue. An engine-agnostic sim core also hedges against engine migration.
- Interest management is mandatory for the infinite world: spatial-hash/grid AOI so each client only receives nearby entities; shard the infinite world into zone processes (one headless Godot instance per zone/match) and let the orchestrator scale them.
- Load-test with headless bot clients early against your real per-zone target (the 40-100 CCU failure range of stock Godot netcode is where you must prove your custom stack); test from Brazilian residential ISPs against sa-east-1/southamerica-east1.
- Hosting: for persistent world zones, Agones (1.59+) on GKE southamerica-east1 or EKS sa-east-1 gives control and no shutdown risk; for burst capacity (weekly tournaments, battle royale) Edgegap's pay-per-use containers are a good complement. Evaluate W4 Cloud (AGPL, self-hostable, Godot-native matchmaking + server orchestration). Keep an abstraction layer over the orchestrator — the Hathora shutdown (May 2026) stranded shipped games.
- Weekly content drops: make items/creatures/skills/biomes data-driven (Resources/JSON) and ship them as PCK patch packs loaded at runtime, with a versioned network protocol so client/server mismatches fail gracefully; be aware PCK patches over-include unchanged resources (use export filters), and iOS forbids executing downloaded code (keep drops data-only there). Server-side content can deploy independently as new container images.
- Given the real-money Pix marketplace, treat server authority as non-negotiable everywhere: all inventory/loot/trade state server-side, combat fully validated server-side (hacked clients become profitable otherwise), and plan rate-limiting/anomaly detection on the item economy from the start.
- If the team were to choose differently: Unity + Fish-Net is the lowest-risk netcode path (mature CSP/lag comp, >100 CCU) at the cost of licensing and a closed pipeline; Bevy + lightyear is the highest-performance path (ECS, WebTransport, bevygap/Edgegap autoscaling exists) but only for a Rust-strong team willing to give up editor-driven weekly content iteration; MonoGame is not recommended for this scope.

## Caveats
- CCU figures are context-bound and partly from commercially biased sources: the ~40 CCU ceiling comes from Rivet's testing as quoted by Ziva's blog, and CipSoft's 80-100 CCU collapse was on a deliberately modest 2-core/2GB VM using the stock high-level API. A custom data-oriented netcode stack on real hardware should do significantly better — but nobody has published a large-scale Godot ARPG proof at this exact profile, so your own load tests are the only real evidence.
- Entity-count claims (hundreds of creatures + projectiles per zone) are extrapolated from Godot's own performance docs and community benchmarks, not from a shipped comparable title; the biggest risk is accidental Node-per-entity architecture creeping back in via content scripts.
- Hosting-platform risk is now demonstrated, not theoretical: Hathora shut down May 5, 2026 after the Fireworks AI acquisition, and Rivet's positioning has drifted toward AI infrastructure. Edgegap is healthy today but is also a single venture-backed vendor; the Agones path trades that risk for meaningful Kubernetes DevOps cost a small studio must staff for.
- Edgegap's São Paulo presence was not explicitly confirmed on their public pricing page (only '615+ locations' across providers whose clouds include São Paulo); confirm Brazil PoPs and measured latency from Brazilian ISPs before committing. Egress at $0.10/GB can dominate costs for a snapshot-heavy ARPG — bandwidth budget per player matters.
- Several Godot 4.6 feature details come from third-party blogs of uneven accuracy (e.g., one claimed Jolt 'replaced Bullet', which Godot 4 never used); verify specifics against official release notes. Similarly, the godot-rollback-netcode Godot 4 port is far less battle-tested than the original Godot 3 version.
- W4 Cloud's hosted SaaS pricing was still undisclosed in the sources found; the AGPL license of the self-hosted version may have implications for your backend code that need legal review.
- The PCK patching workflow has known limitations (duplicate content in patches, clunky export filters — open godot-proposals #146/#6788), and mobile app-store policies restrict executing downloaded code, so weekly drops that add new *behavior* (not just data) may force client store releases on iOS/Android anyway.
- Unity pricing/licensing details (+5% Pro/Enterprise from Jan 2026, modular paid services) may change again; Unity's 2023-24 runtime-fee episode and 2026 'new fee demands' backlash reports suggest ongoing licensing volatility worth watching if that path is reconsidered.
- This research covered engine/netcode only; the Pix marketplace, tournament backend, and anti-cheat/anti-fraud stack (which interact heavily with the server-authority design) were out of scope and can change the hosting architecture (e.g., need for a persistent stateful backend beside match servers).
